# 阶段 0 可行性验证脚本

本目录保存 WebRTC 重构方案的地基验证脚本。它们**不参与构建**，也不被任何工作区引用；
作用是在动手改代码之前，把「方案能否成立」这件事先钉死在可复现的证据上。

保留这些脚本而不是用完即删，原因有二：

1. 结论会被写进 `docs/`，脚本是结论的**证据来源**，必须可重新执行；
2. 将来更换运行环境（换机房、换运营商、换 NAT 类型）时，同一套脚本可再次给出判定。

## 目录内容

| 文件                     | 作用                                                         |
| ------------------------ | ------------------------------------------------------------ |
| `diag-stun.mjs`          | 探测 STUN 服务器可达性，并根据公网映射判定出口 NAT 类型      |
| `verify-datachannel.mjs` | 验证 Node 侧能否建立 DataChannel，并可靠传输字节（含大载荷） |

## 运行

本目录是独立的小包，**不属于 pnpm workspace**（根工作区只收 `apps/*` 与 `packages/*`），
因此需要单独安装依赖：

```bash
cd scripts/poc
pnpm install --ignore-workspace
node diag-stun.mjs
node verify-datachannel.mjs
```

两个脚本都以退出码表达结论：`0` 表示通过（或诊断完成），非 `0` 表示失败。
诊断类脚本即使给出「打洞成功率低」的结论也返回 `0` —— 那是**有效结论**，不是脚本故障。

## 两个脚本分别回答什么

### `diag-stun.mjs`

回答「这个网络环境下 P2P 打洞有没有戏」。判定依据是**同一个本地 socket 对不同 STUN
目标拿到的公网映射是否一致**：

| 观测结果                 | 判定             | 对打洞的含义               |
| ------------------------ | ---------------- | -------------------------- |
| 同一 IP + 同一端口       | 锥形 NAT（Cone） | 成功率高，P2P 可作主路径   |
| 同一 IP + 端口随目标变化 | 对称 NAT（NAT4） | 成功率低，中继回落会是常态 |
| 多个出口 IP              | 多出口           | 基本不可行，只能中继       |

脚本还会识别**被代理 TUN 劫持**的情况：若域名解析到 `198.18.x.x` / `198.19.x.x`
（RFC 2544 保留段，常见于 Clash 等工具的假 IP 池），UDP 会被直接吞掉。
这类失败与网络质量无关，属于代理配置问题，脚本会显式提示。

### `verify-datachannel.mjs`

回答「Node 侧能不能跑 WebRTC 数据面」。依次验证六件事：

1. 创建 `RTCPeerConnection` 与 DataChannel；
2. 交换 SDP 并收集 ICE 候选；
3. 连接与通道进入就绪状态；
4. 正向传输（含 ASCII、中文 UTF-8、二进制）；
5. 反向传输；
6. 256 KiB 分片传输（模拟 HTTP 响应体）。

## STUN 服务器的选择

**只用国内 STUN，不要用 Google STUN。**

`stun.l.google.com:19302` 在国内网络下常被 DNS 劫持或代理 TUN 接管，表现为解析到
`198.18.8.x` 且 UDP 无响应。此时验证失败反映的是代理配置，而不是库或网络的问题，
用它得出的结论没有参考价值。

脚本默认使用以下国内服务器：

- `stun.miwifi.com:3478`（小米）
- `stun.chat.bilibili.com:3478`（哔哩哔哩）
- `stun.hitv.com:3478`（芒果 TV）
- `stun.douyucdn.cn:18000`（斗鱼）
- `stun.cdnbye.com:3478`

**可用性会随时间变化，不要当成常量。** 实测中 `stun.cdnbye.com:3478` 先是可达、
后来变为超时无响应。脚本把 4/5 可达视为正常并继续判定 NAT 类型 —— 判定只需要
能从两个以上目标拿到公网映射，个别服务器掉线不影响结论。

## 依赖

只依赖 `werift@0.24.4` —— 纯 TypeScript 实现的 WebRTC，**零原生依赖**，安装不需要
编译工具链。这一点很关键：它意味着服务端复用同一套 ICE 逻辑不需要引入 `node-datachannel`
之类的原生模块，部署面更干净。

## 实现时必须注意的两条硬约束

这两条是实测得出、且会直接影响后续代码结构的，先记在这里，避免实现阶段重新踩一遍：

### 1. 单条 SCTP 消息上限 64 KiB，必须自行分片

发送超过 64 KiB 的单条消息会被库直接拒绝：

```
max-message-size exceeded: 131072 > 65536
```

因此 HTTP 响应体**不能整块塞进一条消息**，必须按 16 KiB 分片并在对端重组。
脚本按 16 KiB 分片实测通过了 1 MiB 传输，这个分片尺寸可直接沿用。

### 2. 同一个通道端点上 send 与 on('message') 不互通

DataChannel 的两端是配对的：在 A 端 `send` 的数据只会到达 B 端，
在 A 端挂 `on('message')` 只能收到 B 端发来的数据。

本脚本最初就踩了这个坑：步骤 6 用 `inbound.on('message')` 监听，
却用 `inbound.send()` 发送，数据发到了 `outbound`，于是永远收不到，
表现为「超时」而误导人去怀疑库的缓冲上限。**排查接收不到数据时，先核对方向。**

> 顺带排除的伪嫌疑：SCTP 背压。实测 16 KiB × 16 紧循环发送（`bufferedAmount`
> 累积到 262144）全部送达，发送侧不需要额外的背压控制。

## 实测结论

见 `docs/webrtc-p2p-status.md`。要点：Node 侧数据面**可用**；但本机所处网络为
**对称 NAT（单一出口 IP、端口随目标变化）**，因此打洞成功率低，**中继回落是设计内的
常态路径而非异常路径**。这不影响架构成立（回落本来就是设计的一部分），但意味着
P2P 只能当作可选优化，不能当作前提。
